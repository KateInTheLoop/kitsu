# E11 / T3-S5 — the status row, composed once for both renderers

- **UTC start/end:** 2026-10-14T15:25Z / 2026-10-14T16:26Z
- **Branch/base:** `features/tui_herdr_improvements` / `4d85e4a`
- **Epic/story/card:** E11 / T3-S5.
- **Requirement:** **R5**, which this card **amends** (it gained a drop order).
  Records **F50**.

- **What shipped.** `kitsu_render::live::compose_status_row` — model, context
  meter, elapsed, `[N queued]`, ambient tag, one line that never wraps between
  40 and 200 columns — plus the `Surface::queue` seam for queue preview rows,
  and `live::queued_tag` extracted beside `agents_tag`.
  `kitsu-tui/src/status.rs` is a **caller whose production body is four lines**
  and composes nothing.

- **Two conflicts found by reading before briefing, both resolved against the
  code rather than papered over.**

  1. **The plan row asked for a glyph the design forbids.** Its header specified
     `← N agents`; R5 permits that form "once A1's left-arrow affordance exists,
     **and not before**. Promising a key that does nothing is the kind of
     dishonest decoration the rest of this design avoids." The affordance does
     **not** exist — T3-S2's `left_arrow_opens_agents` key is *read* so it is
     not silently unreachable, but **nothing consumes it**, and the pane it would
     open is T4. The bracketed form it is, and the plan row now says so and says
     until when.

     Worth noting what happened here: **the design document protected the
     product from its own plan.** The requirement had written down not just the
     rule but the reason, and the reason is what made the call obvious.

  2. **The composer cannot live where the plan put it.** This is sharper than
     "do not duplicate": `kitsu-render` **cannot** depend on `kitsu-tui`, and
     R5 requires both renderers to share the row's content — so a composer in
     the viewport crate could never serve the classic row. It had to go in
     `kitsu-render`. The precedent was already in the tree: the inline draft row
     is composed through `live::compose_input_row`, with a comment saying that
     seam "is where the two renderers converge on one value type instead of
     drifting apart", and `live.rs:115-123` had already reasoned that the
     viewport's bottom rows are where these segments belong "so running both
     would be duplication before it is a conflict".

     That makes four consecutive cards where the plan's literal instruction
     would have created a second implementation — **F2**, **F38**, **F45**,
     T3-S3's "seam, not a source", T3-S4's refused history parser, and now this.
     The pattern is worth naming: a plan row written early describes the
     *shape* of a solution; by the time it runs, the system often already has
     the mechanism, and the row's wording is the stalest part of it.

- **The drop order, derived honestly and then promoted.** R5 stated **no** drop
  order. The test author derived one from the classic row's precedent — the
  spinner yielding to the draft, an existing test showing the tags outlive the
  spinner, R5's own reasoning that a blocked agent is what the user must act on
  — **labelled it an inference rather than a quotation**, wrote the derivation
  into the test's doc comment, and explicitly invited me to overrule any rung.

  I confirmed it and took its sharper point: an order that lives only in a
  test's doc comment is at the wrong altitude for something every implementer of
  this row must honour. **R5 now states it** — meter, elapsed, model,
  `[N queued]`, ambient tag, with the model truncated before it is dropped —
  along with the reasoning, so an edge case can be judged rather than guessed.

- **The implementation's best property is one the brief did not ask for.**
  Segments are considered in **reverse drop order**, each against the budget its
  betters left, so **a segment freed by narrowing can never fund a wider earlier
  segment** — the drop is monotone in `cols` and nothing reappears as the
  terminal shrinks. That is what makes a 40-to-200 sweep meaningful rather than
  anecdotal; a composer that re-planned at each width could pass every sampled
  column and still flicker between two.

- **The row is NOT yet visible to a user, and the implementer said so rather
  than implying otherwise.** The inline status row still paints the literal
  `"kitsu"` (`main.rs:16576` → `tui_bridge.rs:128`, repainted by
  `paint_draft` whenever the draft is empty). Replacing it needs `status: &str`
  to become live `StatusFields` the guard can re-read, the model, usage, turn
  start, queue depth and agent counts plumbed into the bridge, **and a repaint
  cadence** — elapsed ticks every second, so a static string has no refresh path
  at all. That is state plumbing and a redraw loop, not composition, and doing it
  here would have moved `--test tui`'s pinned bytes that this card was required
  to hold at 19.

- **F50, found by searching rather than assuming:** requirement **A8** ("the
  ambient counter MUST update within 250 ms") is **satisfied and untested**. The
  mechanism is a 50 ms poll tick, comfortably inside budget; the searches for
  `250 ms`, `250ms` and `A8` across `crates/` return **nothing**, and the five
  `agents_tag_*` tests pin the tag's *content*, not its *latency*. "A8 is
  shipped" was true of the mechanism and false of the test. A requirement whose
  number appears nowhere in the suite is one nobody is holding.
