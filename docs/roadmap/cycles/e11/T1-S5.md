# E11 / T1-S5 — `kitsu agents`, the state-file reader

- **UTC start/end:** 2026-10-13T18:07Z / 2026-10-13T19:02Z
- **Branch/base:** `features/tui_herdr_improvements` / `1744eb0`
- **Epic/story/card:** E11 / T1-S5, delivered as **one card** rather than
  split. A parser-only first card would have shipped nothing reachable and
  needed another `allow(dead_code)` window, which the previous story's record
  argued against.
- **Requirement:** H1. The writer from T1-S4 publishes advisory per-process
  state files; this is the command that reads them, completing the loop that
  lets an outside herder see kitsu's agents without screen scraping.

- **Evidence and expected failure:** 19 tests written first — 15 unit, 4
  end-to-end. Observed 34 compile errors (E0425, E0422, E0433) for
  `AgentStateEntry`, `AgentStateEntryStatus`, `list_entries`,
  `format_agents_listing` and `process_is_alive`, plus the end-to-end tests
  failing at runtime on `unrecognized subcommand 'agents'`. The author
  verified behavioural failure with a stub (26 passed, 12 failed) and reverted
  it, noting which three tests pass vacuously against a stub that lists
  nothing and why they remain meaningful against a real reader.

- **In scope:** liveness, the listing, the human rendering, the CLI surface,
  the `--jsonl` refusal, and the documentation.
- **Out of scope:** deleting stale files (a reader must not mutate), and
  extending the `--jsonl` refusal test to the other five callers (finding F8).

- **Authority/failure/version/rollback notes:** host-only and provider-free,
  so it joins `init`, `doctor`, `auth`, `models`, `sessions` and `artifacts`
  outside the inference-run lifecycle described in
  `docs/roadmap/e02-terminal-ownership-audit.md` — no carrier identity, no
  lifecycle publication, no config parse, no network. Rollback is removing the
  subcommand; the reader functions are additive.

- **Forward compatibility is the point of this card**, and it is pinned at
  three levels, because a newer kitsu running alongside an older one must
  never blind the older one's listing:
  1. an unknown file `schema` is reported as schema-unsupported **carrying the
     schema string found**, not dropped — the user learns a newer kitsu is
     running;
  2. an unrecognised top-level field on a known schema does not make the file
     unreadable, which required the read type to avoid
     `deny_unknown_fields` (verified absent);
  3. a thread record that fails to deserialize or fails `validate_default()`
     is counted in `unsupported_threads` while its valid siblings survive.

- **Tests added or changed:** 19 added, none changed. Beyond the three above:
  the pid comes from the filename and a body that disagrees is unreadable,
  since trusting either number would be a guess; a directory named like a
  state file is skipped rather than read as corrupt; ordering is ascending by
  pid and proven against deliberately out-of-order input; a missing directory
  yields an empty list and creates nothing; and the reader is proven to mutate
  nothing by snapshotting the directory around calls that see a live file, a
  stale dead-pid file, a corrupt file and a writer temporary.

- **Implementation:** a `Deserialize`-only read type separate from the
  writer's `Serialize`-only one, with every field optional and `threads` kept
  as raw values so one bad record cannot fail an entry. `ensure_safe_directory`
  is deliberately **not** applied on the read path: the reader mutates
  nothing, so refusing a directory on ownership grounds would only discard
  information. Verified by reading: no mutating filesystem call and zero
  `unwrap`/`expect`/`panic!` in the production half.

- **Review findings and fixes:**
  1. **A failing gate that was the test's fault, not the code's — and the
     implementer refused to paper over either side.** The `--jsonl` refusal
     test asserted empty stdout plus a message on stderr, copied from the
     `--output-last-message` rejection. But that sibling does not pass
     `--jsonl`, and under `--jsonl` kitsu suppresses human stderr and frames
     the terminal error as an event on stdout. The implementer stopped,
     explained the channel contract, and offered options rather than
     weakening the test or diverging from its five siblings. I verified the
     claim directly by running `kitsu --jsonl sessions --json` and observing
     exit 1, empty stderr, and the message inside a stdout `error` event.
     The test was then corrected by its own author, who found and reused the
     existing `jsonl_fixture::inspect_jsonl` helper and matched the shape of
     `test_jsonl_preflight_error_keeps_stdout_machine_only`.
  2. Two properties added at my request after the author flagged them as
     untested: the `--jsonl` refusal itself, and tolerance of an unrecognised
     top-level field. Both would have regressed silently; the second is
     central to this card's purpose.
  3. The author's pid choice is worth recording: `i32::MAX` as the
     "definitely dead" pid, because Linux caps allocatable pids well below it,
     so it can never be reused. That removes the pid-reuse race rather than
     making it unlikely, which spawning and reaping a child would not.
  4. Accepted as convention: `--json` is declared `global = true` to match its
     siblings even though this variant has no subcommand, so the attribute is
     inert. A comment at the site says so, to stop a later reader treating it
     as load-bearing.
  5. Verified myself rather than trusting the report: the bare-array JSON
     envelope follows `sessions`, not the `{"action": …}` object envelope
     `artifacts` uses, which is right because this is a listing rather than an
     action with a result.

- **Residual risk:** liveness on non-unix always answers true, so a listing
  there cannot distinguish a dead process from a live one. Stale files are
  never cleaned up by anyone — the owning process removes its own on clean
  exit, but a killed process leaves one behind forever, and `--all` is the
  only way to see it. A cleanup pass belongs to a later card.
