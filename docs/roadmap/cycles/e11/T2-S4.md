# E11 / T2-S4 — the registry parks, answers, and cannot hang

- **UTC start/end:** 2026-10-14T08:52Z / 2026-10-14T09:55Z
- **Branch/base:** `features/tui_herdr_improvements` / `14a9c85`
- **Epic/story/card:** E11 / T2-S4. Requirements **B3**, **B4**; completes the
  receiving half of **B2**.
- **Records:** **F36**.

- **What shipped.** The registry now receives the requests the gates park:
  `prompt_sender` hands out a channel whose receiver marks the agent
  `Blocked`, advances the generation so watchers see it, and holds the gate's
  reply sender; `answer(id, Decision)` resolves it and restores `Running`;
  `AgentRegistrySnapshot::blocked` is a **real count**; and a 30-minute timer
  resolves `Interrupt` if no answer arrives.

  **Production is still inert** — nothing sets a `Registry` route, which is
  T2-S5's job once the `agents.blocking` config exists to distinguish
  interactive sessions from the scripted, piped and JSONL runs B1 says must stay
  `fail_closed`. That is why the guard test asserting the blocked count is zero
  still passes untouched.

- **B3's no-hang property, by four disjoint routes.** Each *resolves* the gate's
  `oneshot` rather than dropping it: the human's answer; the timer;
  cancellation or teardown; and the registry being dropped, where the receiver
  loop breaks and `Drop` on the sender means `Interrupt` by the request's own
  contract. A request that cannot be parked at all — unknown, terminal, or
  already-blocked agent — is resolved `Interrupt` **synchronously**, so no gate
  can ever wait on a request nobody owns. That last case was not asked for.

- **The finding worth more than the card: F36.** B5 made the *labelling*
  consequence of a new phase explicit, and the compiler enforces it because the
  matches are exhaustive. It said nothing about the **behavioural** consequence,
  which is larger and which the compiler cannot find: every site that asks "is
  this agent finished?" as a **positive** match on `Running` silently answers
  wrong for a blocked agent.

  The implementer enumerated **ten** such sites and widened each. **One was a
  real leak that no test in the card covered**: both prune paths treated
  anything not `Running` as terminal, so a blocked record would have been
  pruned — discarding its parked reply sender and leaving the gate awaiting an
  answer that could never arrive. Found by enumerating sites, not by the suite.

  Equally good: three guards were deliberately **not** widened.
  `finish_with_telemetry`, `record_progress_event` and `steer` keep their
  `Running`-only checks, because resolution restores `Running` before the gate
  wakes — so a timed-out agent's own error reaches `finish` by the normal path,
  which is precisely what makes the end-to-end timeout test pass. Widening those
  would have been cargo-culting the pattern.

- **Two defences nobody asked for.** Each parked request carries a monotonic
  **token**, so a timer firing for an already-answered or re-parked request is a
  no-op rather than spuriously interrupting the *next* question on that agent.
  And `prompt_sender` holds a **weak** reference, so handing a sender to a gate
  can never keep the registry alive.

- **A design decision I endorsed rather than overrode.** Answering an agent that
  is not blocked returns a **distinguished error** — `NotBlocked` versus
  `NotFound` — changing no state. The test author's reasoning: the only caller
  will be `/jobs reply`, a human typing an id into a racy world where the agent
  may have just timed out, been cancelled or finished, so a silent no-op makes
  "nothing happened" indistinguishable from "it worked"; and every other outcome
  enum in this registry (`AgentCancelOutcome`, `AgentPruneOutcome`,
  `AgentHandoffAckOutcome`) is already shaped that way. The state change stays a
  no-op; only the report is explicit.

- **Review findings and fixes:**

     `full` feature genuinely **excludes** `test-util`, so paused-time tests
