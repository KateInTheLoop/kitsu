# E11 / T0-S14 — the viewport's height follows its content

- **UTC start/end:** 2026-10-14T04:18Z / 2026-10-14T04:54Z
- **Branch/base:** `features/tui_herdr_improvements` / `be056c0`
- **Epic/story/card:** E11 / T0-S14. Second of three; **T0-S15** (the palette)
  is next and is what finally requests more than one row.
- **Requirement:** R2, R4 groundwork. Records **F28**.

- **What shipped.** The viewport can be any height its content needs.
  `clamp_viewport_rows` and `fit_viewport_rows` are pure, and
  `BridgeGuard::paint_rows` is one operation that clamps, re-latches if the
  height changed, and paints. Nothing yet asks for more than one row, so this
  card changes no behaviour — `main.rs` still passes a hardcoded `1` and
  today's bytes are byte-identical, which is the regression net.

- **It really was plumbing, as hoped.** `resize(rows, viewport_rows)` from
  T0-S11 already took both dimensions and already decided
  Unchanged/Relatch/Release/Install, so no-flicker-on-unchanged and the
  suspend round trip both fall out of the existing path. `InlineSurface` needed
  no change. The only genuinely new logic is the clamp and the tail, which is
  why both are pure functions.

- **Two decisions I made up front.** A request taller than the window is
  **clamped, not refused** — refusing is right only when not even one row fits,
  which is T0-S11's release case. And when rows must be dropped, **the topmost
  go**, so the composer survives; losing the row you are typing into to make
  room for suggestions would be the wrong trade. The second is pinned by
  asserting the survivors are the **last** of the requested set, in order,
  because getting it backwards is easy and invisible to a test that only counts
  rows.

- **One refinement on my sketch, from the test author.** `fit_viewport_rows`
  returns the surviving **tail slice** rather than a count, so its `len()` *is*
  the height and the two cannot disagree even inside the implementation. A
  property test ties the clamp to `show` directly — every non-zero clamp must
  be a height `show` actually latches — which is the same trick that made
  `plan_resize` trustworthy.

- **Review findings — two of them against my own brief:**
  1. **My "by construction" shape was wrong and the implementer refused it,
     correctly.** I specified that `paint_draft` route through `paint_rows` so
     the painted count could not disagree with the latched height. **Two
     pre-existing tests forbid it, and I verified both rather than taking the
     report:** one pins a *one-row* paint into a viewport that stays *3 tall*
     after a resize; the other pins **zero bytes** when the terminal is below
     the bound. Through `paint_rows` a one-row draft clamps to 1 and
     re-latches, contradicting the first, and the second would emit bytes. The
     two are genuinely different operations — `paint_draft` draws into whatever
     viewport exists, `paint_rows` lets content choose the height. Recorded,
     including that this is not permanent: with a palette open a keystroke must
     repaint *all* rows, so `paint_draft`'s single-row semantics becomes wrong
     exactly when the palette lands. That reconciliation is T0-S15's.
  2. **A bug my shape would have introduced**, caught by the implementer and
     not asked for: an early return when the clamp is zero. `resize(2, 0)` is
     `Install`, and `show(2, 0)` would latch a **full-screen** region — "no
     rows fit" silently becoming "the region is the whole screen". Zero now
     leaves the latched geometry alone.
  3. Accepted `#[cfg_attr(not(test), allow(dead_code))]` scoped to
     `paint_rows`, with a comment: the palette is its first production caller
     and inventing one early would be worse.
