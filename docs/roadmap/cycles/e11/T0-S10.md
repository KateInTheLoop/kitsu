# E11 / T0-S10 — Tab accepts the inline slash hint

- **UTC start/end:** 2026-10-14T02:05Z / 2026-10-14T02:55Z
- **Branch/base:** `features/tui_herdr_improvements` / `85a8cab`
- **Epic/story/card:** E11 / T0-S10
- **Requirement:** **R4**, further — its status note is updated again.

- **What shipped.** Tab at the inline idle prompt accepts the slash-completion
  suffix the row is showing, so `/s` + Tab becomes `/steer`. That is parity
  with the during-turn row, and deliberately nothing more: no completion lists,
  no cycling, no `@file` paths.

- **Why it was a card at all.** The during-turn collector's entire Tab handling
  is seven lines, and the inline reader was simply dropping the action. I had
  sized this correctly in T0-S9 *after* getting it wrong twice before that, by
  reading what `typeahead_slash_hint` actually returns rather than a summary.

- **The trap, and that it was proven rather than argued.** The inline reader's
  hint is *either* the slash suffix *or* the reverse-search status. An
  implementation that appends "the current hint" types
  `⌕ reverse-search '…'` — leading spaces and all — into the user's prompt. I
  flagged it in the brief; the test author did better than take my word and
  **implemented the naive version to prove its test bites**, reporting the
  resulting draft verbatim as `"deploy the thing  ⌕ reverse-search 'dep'"`.
  So the suite distinguishes the correct implementation from the plausible
  wrong one, which is the only thing that makes such a test worth having.

  It also found *why* the trap is reachable rather than theoretical: actions are
  processed after a whole `feed` returns, so a single read such as
  `"\t\x12dep"` delivers `CompleteRequest` at a moment when a later Ctrl+R in
  the same read has already armed the status and rewritten the buffer.

- **Where the agent improved on my specification.** I asked it to pin "Tab does
  nothing during a reverse search". It pinned something better and told me why:
  the editor treats any control key in search mode as **accept the match, exit
  search, re-feed the byte**, so by the time the reader sees `CompleteRequest`
  the search is over and the draft is the matched history line — not a slash
  prefix — so the correct arm is naturally a no-op. That is readline's "accept
  and act", and an explicit "if searching, ignore Tab" guard would have
  contradicted the editor's own rule. My version would have been wrong.

- **Review findings and fixes:**
  1. The implementer found a **third** stale comment and stopped rather than
     edit it unasked, since my brief authorised exactly two. Correct call, and I
     fixed it as reviewer. It claimed Tab "is explicitly dropped: that loss is
     real" — false as of this card — *and* that the paint seam could not carry
     the search status, which **T0-S9 had already fixed and I missed**.
  2. Worse, the test that comment introduced was named
     `inline_read_cannot_paint_the_reverse_search_status_line` and its failure
     message said "if this now fails the seam was widened and the documented gap
     should be closed". The seam *was* widened a card earlier and the message
     never fired, because the assertion inspects the **draft** rather than the
     hint. So it was a correct assertion wearing a false name and a false
     rationale. Renamed to
     `inline_read_never_lets_the_search_status_become_draft_text` with the
     assertion **byte-identical**: what it guards did not disappear when the
     seam was widened, and it matters *more* now that Tab exists.
  3. Both of the implementer's technique notes were followed and verified:
     `typeahead_slash_hint` called directly rather than `hint_of`, and the
     repaint flag set explicitly rather than leaning on the hint-difference
     condition, which would not fire for an accept that left a non-empty hint.
