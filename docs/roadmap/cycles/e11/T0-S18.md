# E11 / T0-S18 — the flaky test was telling the truth

- **UTC start/end:** 2026-10-14T06:20Z / 2026-10-14T07:21Z
- **Branch/base:** `features/tui_herdr_improvements` / `7efe8ae`
- **Epic/story/card:** E11 / T0-S18
- **Requirement:** none — a **production bug fix**, found through a test flake.
  Resolves **F28**; records **F31** and **F32**.

- **Why I spent a card on a flake instead of starting T2.** The whole loop's
  value rests on test evidence being trustworthy, and I had documented two cases
  where it was not. A suite that fails 1 in 12 trains everyone to re-run until
  green, which is precisely how F23's 7% flake hid for weeks. I also verified
  before starting that the flake **predates this branch**: the test exists on
  `main` at the same path and this branch has never touched that file.

- **The flake was a true positive, and three readings of it were wrong — mine
  included.** An earlier agent guessed a `#[serial]` gap. I narrowed it to
  "cross-module interference, some other test mutates shared state", which was
  right in *shape* and wrong in *kind*. The diagnosis found the real cause:

  `flock` locks live on the **open file description**, not the descriptor, and
  `O_CLOEXEC` closes at **`exec`, not `fork`**. So while any sibling thread
  sits between `fork` and `execve`, its child holds a duplicate of our lock fd
  and therefore holds the lock. Both lock sites treated the first
  `EWOULDBLOCK` as proof of contention, so an uncontended acquisition failed
  spuriously. Proven independently of kitsu with a standalone probe: **5.5%
  spurious failures**.

  **This is user-facing.** kitsu spawns tool subprocesses, agent hooks and
  `git` on other threads as a matter of course, so a real session commit could
  report `session '<id>' is already active in this or another process` when
  nothing of the kind was true. `#[serial]` would have fixed none of it.

- **Scale, measured rather than estimated.** Four runs at
  `--test-threads=256` gave 17, 16, 28 and 7 failures, unioning to **46
  distinct tests — every one in `session::*`, none elsewhere**, which is exactly
  the distribution the fence hypothesis predicts.

- **Two sites, and that was proven rather than assumed.** The test author found
  the second — `SessionLease::acquire` — while verifying, and demonstrated that
  a retry at the first alone left `session::tests` failing. **A one-site fix
  would have turned the new regression test green while leaving most of the 46
  exposed**, which is the most dangerous kind of partial fix.

- **Why the apparently-better fix was unavailable, checked rather than assumed.**
  `fcntl` `F_SETLK` record locks are not inherited across `fork`, which would
  remove the cause outright — but they are **per-process**, and I verified that
  same-process detection is load-bearing and tested:
  `head_cas_requires_the_exact_fence_and_revision_then_advances_old_to_new`
  takes a fence and re-takes it **on the same thread of the same process**,
  requiring the second to fail. Record locks would let that succeed.
  `F_OFD_SETLK` inherits identically. So the fix is a bounded retry, and the
  code says plainly that it is a **mitigation, not a guarantee**.

- **Review findings and fixes:**
  1. The budget was chosen **empirically after a first attempt failed** — a flat
     64 × 50 µs still left failures at 256 threads. The shipped split (32 × 50 µs
     then 47 × 500 µs, ~25 ms worst case) clears an ordinary single fork window
     cheaply and only pays the long phase for overlapping windows. That is the
     right way to pick a constant: measure, do not guess.
  2. The cost lands where it should and was quantified: suite wall time 0.19 s →
     0.30 s, because ~40 contended-case assertions each now pay the budget
     before getting the error they want.
  3. The exhaustion message is byte-identical — the helper returns the kernel's
     own error and both call sites keep their original checks and strings, so the
     ~40 `"already active"` assertions still hold.
  4. **The implementer found a third site and reported it instead of fixing it**
     (F32), correctly: it was outside its scoped files. I deferred it one card
     rather than patching it myself, so its regression test comes from a
     different agent than its fix — the cost is one known-rare flake, already
     recorded, against the cost of a third fix with no evidence it worked.
