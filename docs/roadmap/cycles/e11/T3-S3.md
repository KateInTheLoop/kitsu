# E11 / T3-S3 — one completion source, two hosts

- **UTC start/end:** 2026-10-14T14:05Z / 2026-10-14T15:29Z
- **Branch/base:** `features/tui_herdr_improvements` / `9bad223`
- **Epic/story/card:** E11 / T3-S3.
- **Requirement:** **R4**'s remaining list half. Settles **F20** (third pass).

- **What shipped.** The inline composer gained `@file` path completion, slash
  completion, a hint and a highlighter — and both it and the classic rustyline
  prompt now read from **one** completion source, `ComposerCompletion`, with a
  test sweeping every prefix of every registered command requiring all three to
  agree.

- **The insight that shaped the card, and it was the test author's, not mine.**
  My brief asked for a design where a future fork fails the test. The author
  sharpened it: **"the trait is a seam, not a source."** Defining
  `CompletionSource` in `kitsu-tui` gives you a seam across the crate boundary;
  it does not by itself stop anyone writing a second implementation behind it.
  So the single source is a type in `kitsu` that both hosts call, and the trait
  impl in `tui_bridge.rs` is a **one-line delegate**. That mirrors a precedent
  already in the repo — `slash_palette_rows` is the one palette renderer, with a
  comment saying "there is deliberately no second palette renderer".

- **The dependency direction was verified from the manifests, not assumed.**
  `kitsu` depends on `kitsu-tui`; `kitsu-tui` cannot depend on `kitsu`, which
  is a bin-only package. So the plan's shape was the only one that compiles, and
  nothing had to move. Checking that first is why no time was lost to a design
  that could not build.

- **A fork is caught three independent ways**, which is what distinguishes this
  from a two-path parity check:
  1. **Sentinel tests in `kitsu-tui`** drive the composer with a stub source
     returning values no real completion could produce and require the output to
     be that answer element-for-element, including the replacement offset. **Any
     completion or styling logic added to `kitsu-tui` kills the sentinels.**
  2. **A sweep over every byte-boundary prefix of every entry in the live
     `SLASH_COMMANDS` registry**, requiring classic == shared == inline at each,
     with the checked count asserted to be at least the registry length so it
     cannot pass by iterating nothing. The domain grows every time a command is
     added.
  3. **Equality against the registry itself**, non-emptiness asserted first, so
     two hosts agreeing on an empty list fails.

  The author also **labelled the honest limit**: equality tests cannot *prove* a
  single call site — only review can. What they do is make a behavioural fork
  fail immediately across the whole registry domain, and make a duplicated
  implementation pointless.

- **A design change that earned its keep.** `ComposerCompletion` **holds** the
  launch directory instead of reading `current_dir()` inside the call, as the old
  code did. That makes the candidate list a pure function of its inputs, which is
  what lets the acceptance test be pure and parallel-safe with **no
  `set_current_dir` anywhere** — a test that mutates process-wide state is a
  test that cannot run beside its neighbours.

- **Hint parity is deliberately NOT host-equality.** **F20**'s second correction
  established that the classic multi-row deck and the inline row suffix are
  different things with different causes. So the inline hint is pinned as the
  shared row hint and host-equality applies only to the **highlighter**, where it
  genuinely matters because rustyline computes hint width from the unstyled text.
  One test passes on arrival, as a declared guard rather than a test that failed
  to fail.

- **Review: a fourth evidence-based override of my instructions, and it was
  right.** I wrote "leave `attachments::complete` for other callers". The
  implementer found it had **no** remaining callers once `impl Completer` routed
  through the shared source, so leaving it would have tripped the zero-warning
  gate — and a second launch-directory reader is exactly the duplication this
  card removes. It deleted the function and offered to restore it. **I verified
  at HEAD that it had exactly one caller: the very function body this card
  replaced.** My instruction rested on an assumption I had not checked.

- **The redundant handle retired at review.** `ChatHelper::permissions` survived
  the implementation only because a test helper initialised it, and the
  implementer could not remove it without editing a test — so it kept it behind
  `#[allow(dead_code)]` and **flagged it as the F45-shaped second handle on the
  same input**. That is exactly right: two handles on one input is how drift
  starts. I removed the field at all three sites, including the test helper's
  initialiser, and verified 819 tests still pass with clippy silent and no marker
  left behind.
