# E11 / T0-S1 — extract the type-ahead editor into its own crate

- **UTC start/end:** 2026-10-13T19:07Z / 2026-10-13T19:51Z
- **Branch/base:** `features/tui_herdr_improvements` / `d319e57`
- **Epic/story/card:** E11 / T0-S1, one card. First story of milestone T0.
- **Requirement:** none directly. This is the **blocking prerequisite** the
  plan review identified: `crates/kitsu` is binary-only, a library crate
  cannot import from a binary, and the planned `kitsu-tui` needs the same
  editor the binary's input collector uses. Nothing in T0 could start until
  the editor became a library.

- **How TDD applies to a pure move.** There is no feature to drive, so the
  artifact is an **integration** test in the new crate. That choice is the
  substance of the card rather than ceremony: an integration test compiles as
  an external consumer, so it can only reach genuinely public items, which is
  exactly the property a crate extraction must establish. The 39 existing unit
  tests are the behavioural net and travel with the code unchanged; the
  integration test is the surface net.

- **Evidence and expected failure:**

  ```
  error[E0432]: unresolved imports `kitsu_editor::EditorAction`,
  `kitsu_editor::FeedOutcome`, `kitsu_editor::TypeaheadEditor`
  ```

  Nine integration tests exercising all three public types, all seven
  `EditorAction` variants by name, and every one of the eleven public methods.

- **What the integration test caught that my own survey missed.** I inspected
  the module and reported that its public surface was already exactly right
  and "nothing needs widening". That was wrong in one place:
  `TypeaheadEditor::new` was `#[cfg(test)]`-gated. It is `pub`, and the 39
  unit tests use it, so it looks public — but a unit test compiles under
  `cfg(test)` while an integration test links the library built without it, so
  the constructor was invisible from outside. Keeping it test-only would also
  have forced the future terminal UI to pass a dummy `String` to build a fresh
  editor. The attribute was removed and replaced with a doc comment. This is
  precisely the class of same-crate coupling that only an external consumer
  reveals, and it justifies the integration test over simply moving the 39.

- **In scope:** the crate, the move, the one attribute removal, the dependency,
  the call sites, and the documentation.
- **Out of scope:** everything else in T0 — the renderer crate, the viewport,
  the `Surface` seam.

- **Authority/failure/version/rollback notes:** no behaviour change, no
  authority surface, no new dependency anywhere (the crate has no
  `[dependencies]` section at all, because the module's only external name is
  `std`). Packaging note for a future release: if the internal crates are ever
  published, this one must be published too, since `kitsu` now depends on it.
  Rollback is moving the file back and reverting 21 lines.

- **Acceptance arithmetic.** A refactor's one real risk is losing tests in
  transit, so I captured the baseline before the work started and required
  exact numbers rather than "green":

  | Measure | Before | Required | Actual |
  |---|---|---|---|
  | `cargo test -p kitsu --bins` | 676 | 637 | **637** |
  | `cargo test -p kitsu-editor` | did not exist | 39 + 9 | **39 + 9** |
  | workspace total, all targets | 1783 | 1792 | **1792** |

  Both profiles for every count. Plus `-p kitsu --test cli` 229 unchanged,
  clippy zero warnings, formatting clean.

- **Byte-identity, verified myself rather than accepted.** I extracted the old
  body from `HEAD` and diffed it against the tail of the new `lib.rs`: 1208
  lines, exactly one differing line, the `#[cfg(test)]`-to-doc-comment swap.
  Visibility is likewise unchanged: 16 `pub` items and 60 private methods in
  both the old file and the new one.

- **Review findings and fixes:**
  1. The test author pre-verified the whole move in a scratch copy — 39 unit
     tests and 9 integration tests passing against a standalone build with
     only the `cfg(test)` line stripped — so the specification was known
     sound, and the one required widening was known, before the implementer
     started.
  2. **A documentation regression I caught and repaired.** The old module
     carried a 29-line header that was a complete keymap inventory: every
     binding, the lone-Escape escape-time tradeoff and its ~50ms quiet-poll
     resolution, the reverse-i-search semantics, and the bracketed-paste rule.
     The move dropped it in favour of the skeleton's shorter crate doc, and the
     implementer flagged that as a doc decision rather than silently discarding
     it. I folded the inventory into the crate documentation under a "Supported
     keys" heading. Losing it would have been exactly the kind of drift the
     standing documentation requirement exists to prevent, and it matters more
     now than before: the crate is the contract between two consumers.
  3. The implementer also rewrote a rustdoc intra-doc link in `main.rs` that
     pointed at the old module path, which is the 21st line of that file's
     diff and would otherwise have become a broken link.

- **Documentation (standing requirement, in this commit):** `design.md`'s
  canonical workspace list gains the crate with the reason it is separate; the
  plan's progress table records the story done and notes T0 has begun with its
  prerequisite; the crate's own docs carry the keymap inventory. **No
  `CHANGELOG.md` entry, deliberately:** Keep a Changelog records user-visible
  change, and this alters no behaviour, no command, no flag and no config. The
  omission is reasoned, not an oversight.

- **Commit:** see below.
- **Residual risk:** none behavioural — the identical 39 tests pass in the new
  location in both profiles and the workspace total accounts for every test.
  The remaining exposure is organisational: `kitsu-editor` is now a public
  surface two consumers depend on, so widening it later is cheap and narrowing
  it is not.
