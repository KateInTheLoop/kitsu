# E11 / T0-S15a — the palette's rows, built to the height they will get

- **UTC start/end:** 2026-10-14T04:52Z / 2026-10-14T05:21Z
- **Branch/base:** `features/tui_herdr_improvements` / `7dcd8f7`
- **Epic/story/card:** E11 / T0-S15a. **T0-S15 split on contact**: this card is
  the rows as data, S15b is the wiring.
- **Requirement:** R4. Records **F29**.

- **The card got much smaller once I read the code.** `slash_palette` already
  existed and already did the hard parts: matching, the bordered box in both
  Unicode and ASCII frames, a row cap, a trailing "N more" row, the no-match
  case, and per-row width fitting with ellipsis. So this card **reuses** it
  rather than inventing a second palette — two palettes that drifted would be
  worse than one with an awkward call site.

- **The problem the card actually exists to solve.** T0-S14 drops the
  **topmost** rows when content does not fit, so the composer survives. That is
  right for a list and **wrong for a bordered box**: the top row is the frame
  and its label, so dropping it leaves a box with no lid. The palette therefore
  has to be **built to the height it will be granted**, which is why
  `granted_rows(requested)` exists as a query answered *before* layout.

  Worth noting that this shape was arrived at twice from different directions —
  once so a palette could mark its hidden entries without painting, discovering
  it was clamped, and repainting (a visible flicker), and once here to keep the
  frame intact. Converging on the same answer from two problems is reassuring
  about the decomposition.

- **The detail most likely to be quietly wrong, and how it is pinned.** The
  existing renderer emits its "N more" count from the **row cap**. The height
  can hide entries too, so a count that ignored it would under-report exactly
  when the window is short — wrong in a way that looks right. The test author
  pinned it **relationally** against `matching_slash_commands(prefix).len()` at
  every height, so a count derived from the cap fails immediately. At the
  minimum height with many matches the box is border + a "N more" row carrying
  the **full** count + footer: three rows, well formed, honest.

- **Parity is asserted against the classic renderer itself**, not against
  literals — two widths, both frames, at the exact height and at exact + 5 (so
  extra height adds nothing). That is what makes "reuse" checkable rather than
  aspirational.

- **A detail the test author found by reading the surrounding rendering:** the
  minimum viable box is **three** rows, not four, because `slash_palette` ends
  at the `├…┤` separator and the composer status line supplies the `╰…╯` that
  closes it. It also checked the decline rules — empty buffer, non-slash text, a
  completed command with arguments, trailing or leading space, anything with a
  newline — against `ChatHelper::hint`'s own behaviour instead of inventing
  them.

- **Review findings and fixes:**
  1. **I accepted duplication, on evidence rather than assumption.** The
     re-derived row-selection step drags along copies of both labels, both frame
     sets and the no-match text — the very thing that made T0-S9 share a
     composer instead of reimplementing it. So I tested whether the parity net
     actually bites: changing the label in `slash_palette` **alone** turns the
     parity test red, then reverting returns 712 green. The duplication
     therefore costs a double edit that fails loudly, not a silent divergence.
     Accepted, with the proper factoring recorded as **F29** and assigned to
     S15b, which touches this code anyway: give the classic renderer the height
     parameter and make `slash_palette` a thin join over it, exactly as
     `compose_input_row` wraps `compose_row`.
  2. Verified rather than assumed: `main.rs` needed **no** visibility change,
     and the card touched one file.
