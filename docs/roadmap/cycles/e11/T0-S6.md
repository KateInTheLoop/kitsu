# E11 / T0-S6 — the go/no-go record for the inline renderer

**Verdict: GO on region-flow for the opt-in preview. NO-GO on making it the
default**, pending one measurement I cannot take here and two known regressions.

This is the record milestone T0 was built to produce. T0 existed to answer four
questions cheaply enough that a wrong answer cost a few cards rather than a
rewrite. Three are answered with measurements; the fourth is handed over,
honestly, as a checklist.

## Q1 — does native scrollback survive a scroll region? **UNRESOLVED, handed over**

**Not answerable from this repository**, and I will not guess at it. The
question is whether a terminal's own scrollback retains lines that scrolled out
of a DEC scroll region. Finding F13 established that the `vt100` emulator the
suite uses cannot answer it: its `Grid::scroll_up` pushes a row to scrollback
only when **no** region is active, and the viewport always sets one, so
region-scrolled rows are discarded by construction. A test pins that limitation
negatively, so it lives in code rather than folklore.

That is not a flaw in `vt100` — the VT spec does not define the behaviour, so
every terminal decides for itself. Which is exactly why it must be measured on
real terminals instead of reasoned about.

`terminal-matrix.md` in this directory is the executable handover: the commands,
the per-terminal observations, the ten terminals and two multiplexers to cover,
and — fixed **in advance**, so an inconvenient result cannot be rationalised
afterwards — the decision rule that maps each outcome onto a mechanism choice.

**This is the single open item gating the default.**

## Q2 — ratatui's inline viewport, or paint it by hand? **ANSWERED: by hand**

Decided, and the plan pre-committed to this fallback before any code existed
("ratatui inline viewport fights the scroll region → pre-decided fallback:
manual viewport + ratatui overlays only"). What was built is the manual
viewport: `crates/kitsu-tui/src/viewport.rs`, around 500 lines of production
code under 33 tests, with no ratatui on the path at all.

Two pieces of evidence that this was right rather than merely expedient:

- **The mechanisms genuinely conflict.** ratatui's inline viewport manages its
  own cursor and redraw region; the design here needs a *permanent* scroll
  region that the terminal itself scrolls, with the viewport pinned outside it.
  Running both means two owners of the same rows.
- **Coupling deeper to ratatui has a measured cost.** In T0-S2 the `vt100`
  version this project wanted was unusable because ratatui pins
  `unicode-width` to an exact `=0.2.0`; the pin had to drop to `vt100` 0.15 to
  resolve it. A dependency that constrains the test emulator's version is one to
  keep at arm's length from the render path.

ratatui stays available for overlays — a full-screen agent view in a later
milestone — where it does not fight for the same rows.

## Q3 — must every writer be routed through the seam first? **ANSWERED: no**

**The most valuable answer in this milestone, and the one that removed its
largest cost.** `main.rs` holds several hundred direct `println!`/`eprintln!`
calls, mostly slash-command output. The fear was that a pinned viewport would
require routing all of them through the render seam before inline mode could
work at all.

It does not. Measured twice, on a real pseudo-terminal, not reasoned about:

- **Cooked mode (T0-S5b).** With the viewport installed, all forty-odd lines of
  `/help` printed through direct writes that bypass the seam entirely, and the
  pinned status row survived intact. A direct write inherits the terminal's
  cursor, the cursor is parked *inside* the region, and the terminal scrolls the
  region on a line feed regardless of which code wrote the bytes. The assertion
  is guarded by requiring twenty non-blank rows above the viewport, so it cannot
  pass vacuously.
- **Raw input mode (T0-S5d).** The condition on the above was cooked mode, where
  the terminal supplies the carriage return. Resolving F14 showed the premise
  was too broad: there are two raw modes here. `crossterm`'s goes through
  `cfmakeraw` and clears `OPOST`/`ONLCR`; the live row's own `RawStdinGuard`
  touches **only `c_lflag`** and leaves the output flags alone. The idle reader
  reuses the latter, so the terminal still supplies the return and nothing
  staircases — measured with the guard demonstrably engaged, child emitting
  `\n`, master reading `\r\n`.

So the writer census that this card was originally scoped to perform is **not
needed**, and the `insert_history` mechanism it would have justified stays
unbuilt. The residual exposure is narrow and worth stating plainly: any future
code that reaches for crossterm's raw mode on the binary's path would clear
`OPOST` and break every one of those writers at once. A regression test guards
the alignment, and its precondition fails if the classic prompt is still
running, so it cannot silently degrade into re-measuring the easy case.

## Q4 — paste latency. **ANSWERED: 1.83 ms**

A 10 KiB bracketed-paste block through the real idle reader and the real editor:

| Profile | Elapsed |
|---|---|
| debug | **1.83 ms** |
| release | **124 µs** |

Fed in 1 KiB reads, which is the honest shape: the reader's buffer is 1 KiB, so
a real terminal can never hand the editor more however it writes. The block
stays **one** draft with newlines and tabs preserved exactly, which is the
design requirement; the regression bound is a deliberately loose 5 s, because
the test exists to catch a quadratic insert path (which would overshoot by
orders of magnitude) rather than to police microseconds and flake on a loaded
machine.

No paste concern remains for this path.

## Mechanism decision, for design §4.2

**Region-flow**, as implemented. `insert_history` is **not** built.

The two mechanisms trade against each other on exactly the two questions above:
`insert_history` buys native scrollback (Q1) at the price of routing every
writer (Q3). Q3's answer removed region-flow's cost without removing
`insert_history`'s price, so region-flow wins on current evidence — but Q1 is
the one input still missing, and it is the input that could overturn this. The
matrix's decision rule states in advance what each outcome means, and the
fallback remains deliberately unbuilt rather than speculatively written.

## What blocks the default

1. **Q1** — the terminal matrix. Unmeasured; everything else is contingent on
   it. **This is now the only blocker that cannot be cleared from inside this
   repository**, since F21 is resolved and F20 has shrunk to one seam.
2. **F20, as corrected in T0-S8** — the preview's idle prompt lacks the
   slash-command palette and Tab completion. **Two items originally listed here
   were wrong:** cross-session history works, and so does reverse search. See
   F20's correction; the false claims had also reached the README, the
   changelog and a production comment.

   What remains is narrower and more tractable than this record first said. Tab
   completion, the palette and the reverse-search status indicator share **one**
   cause — all three render into the during-turn row's hint slot, and the inline
   paint callback is `(draft, cursor)` with nowhere to put a hint. So the
   blocker is not "the inline prompt is missing most of what rustyline gave it"
   but "the inline paint seam carries no hint slot", and one seam change
   addresses all three.
3. ~~**F21** — Ctrl+Z is swallowed~~ **— resolved in T0-S7**, and covered end
   to end in T0-S8 (F22).

`KITSU_TUI` unset remains byte-identical to the pre-viewport renderer, which the
unchanged 229-test CLI suite demonstrates on every commit. That is what makes
shipping the preview safe while these stay open.
