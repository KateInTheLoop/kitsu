# E11 / T0-S12 — the resize tests that catch a silently-dead feature

- **UTC start/end:** 2026-10-14T03:12Z / 2026-10-14T03:53Z
- **Branch/base:** `features/tui_herdr_improvements` / `9a5e789`
- **Epic/story/card:** E11 / T0-S12. A **test-only** card: the feature already
  worked, and what was missing was the coverage that proves it keeps working.
- **Requirement:** none new. Resolves **F25**, moves **F24** into CI, records
  **F26**.

- **The point of the card, and a correction of my own reasoning.** One card
  earlier I wrote that F24 — the resize feature silently dying if the signal
  handler is installed with `SA_RESTART` — could only be caught by a human at a
  real terminal. **That was wrong.** The property is untestable *in-process*,
  because a raise from the same thread never blocks in `read`; it is perfectly
  testable from outside, because the harness signals a **separate process** that
  is genuinely blocked in a real `read` on a real tty. With the flag set, the
  child never wakes and the test fails. That is a limitation of unit tests, not
  of testing, and I had generalised from the wrong one.

- **The design constraint that decides whether such a test is worth anything.**
  No input may follow the resize before the assertion. A keystroke after the
  resize wakes the blocking read by itself, the flag is then checked, and the
  viewport resizes *even with `SA_RESTART` set* — so a test that types
  afterwards passes under both installations and establishes nothing. I put this
  in the brief as the thing to get right, and the author achieved the stronger
  form: **the gate on sending the next byte is the new geometry appearing in the
  stream.** If the flag were only checked on the next keystroke there would be no
  next keystroke, the trigger would never fire, and the test fails on its
  deadline with the transcript attached.

- **It proved the discrimination rather than asserting it.** With
  `action.sa_flags = libc::SA_RESTART` set temporarily, all three tests failed;
  restored, all three pass. That is the difference between a test that looks
  like a regression guard and one that is.

- **What shipped:** three tests — the signal-alone re-pin (the F24 regression
  test, whose doc comment names `SA_RESTART` and says not to delete it as
  redundant with the unit tests, because those pin the decision and the bytes
  while this one pins the *delivery mechanism*); the release case, shrinking
  below the minimum height and asserting the region is reset with no DECSTBM
  whose margin exceeds the new screen; and the round trip, two resizes with zero
  input between them, ending correctly pinned with a draft typed before the
  first resize and never retyped.

- **The harness change that was genuinely necessary.** `Session` no longer
  holds a fixed-size emulator: it replays the stream in segments and calls
  `vt100::Parser::set_size` at exactly the byte offset where the child was
  resized. Without that split, every post-resize absolute address is modelled
  against the old grid and **silently discarded** — the tests would have been
  asserting against a screen the emulator never drew. Also: a `Step` action
  that sends no bytes, `set_window_size`, and `raw_between`, the window of
  bytes the child wrote in response to a signal alone, which is what the
  assertions are built on.

- **A measured root cause worth keeping.** `TIOCSWINSZ` on this pty master
  delivers no signal at all, so the explicit `kill` is required and there is no
  double delivery. The author measured it by removing the `kill` and watching
  all three tests deadline. The reason: the kernel signals the tty's *foreground
  process group*, and this pty is nobody's controlling terminal — the child
  takes the descriptors by `dup` and never calls `TIOCSCTTY`, so there is no
  process group to signal.
