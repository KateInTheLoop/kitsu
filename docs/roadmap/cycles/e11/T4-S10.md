# E11 / T4-S10 — one table, and the keyboard swept to prove it

- **UTC start/end:** 2026-10-15T14:00Z / 2026-10-15T16:12Z
- **Branch/base:** `features/tui_herdr_improvements` / `b599d98`
- **Epic/story/card:** E11 / T4-S10. Records **F82**.
- **Requirement:** **§4.7**; `docs/ux-design.md`'s glyph row corrected.

- **What shipped.** `crates/kitsu-tui/src/keys.rs` holds **13 rows** — label,
  presses, kind, description — and **both** the overlay's `?` help and the new
  `/help keys` render it. The help literal is gone: `overlay_help_rows` now
  iterates `BINDINGS` and holds **zero** key literals (verified). Both readers
  share one row formatter, so they cannot lay the same table out two ways.

- **The table cannot be the dispatch source, and an exhaustiveness test would
  have been worthless.** `OverlayKey` is private to the binary and `match` arms
  are not data, so `kitsu-tui` can neither be the match nor enumerate it — and a
  guard reading the dispatch's own source **cannot fail when the dispatch
  disagrees with it**, which is exactly why **F57**'s own guard was unwritable.

- **So the guard enumerates the keyboard instead.** Every key the decoder can
  produce — all of `0x20..=0x7e` plus the arrows, `Enter`, `Backspace` and a
  resolved `Esc` — pressed on a fresh view, asking **the painted frame** whether
  anything happened, checked in **both** directions against the table. **It reads
  neither source, so it cannot agree with the dispatch by construction.** F57's
  trap solved rather than worked around.

- **It found three keys dispatched and advertised nowhere**, which I verified:
  **`q`** closes the view, **`Enter`/`→`** attach. Fifteen presses dispatched,
  twelve advertised.

  **This is the defect T4-S3, T4-S4b, T4-S5 and T4-S7 each closed once, open in
  triplicate.** All four applied the rule *a key that works while unadvertised is
  half-shipped* — and each applied it **only to the key it was adding**. Four
  correct applications left three violations standing. **A rule applied
  per-change is not a rule enforced**; the fix was never more diligence per card
  but one test that asks for all keys at once.

- **The sweep's limits are stated, not glossed.** It asks *did something happen*,
  not *did the right thing happen* — the earlier cards' per-key behaviour tests
  remain the only guard on **what** each key does and were left untouched. It
  also misses keys that act only from a non-fresh state, and the whole composer
  chord surface. **Naming the gaps is part of the guard being trustworthy**: a
  sweep described as total would invite the false confidence F57, F69 and F75 are
  about.

- **The table expresses kinds, and the kinds have consequences.** Six variants,
  each asserted **with its effect on the painted description** — so a kind that
  is only a struct field fails: `x` → `TwoPress` *and* its text says "twice";
  `r` → `DecisionRead` *and* its text names `y`/`a`/`n`; the four line-openers
  carry their grammars; `?`/`esc` → `View`. **`up/dn` is one row with two
  presses**, not two rows, and `Enter`/`→` took the same shape — two rows would
  describe one movement twice and let the pair drift.

- **Last card's vacuity lesson was carried forward unprompted.** The
  help-equals-table assertion adds `!painted.is_empty()`, because **the one way
  an equality holds vacuously is both sides empty** — precisely how T4-S8's
  acceptance test accepted an implementation that painted nothing.

- **Corrections.** `/help keys` is **not** a new command: `/help`'s arm already
  forwards any argument, so F57's unregistered-arm hazard could not arise, and
  the half that mattered was **registration** — its `args` was `""`, so nothing
  offered `keys` in the listing, the palette or either completion host. Now
  `"[command|keys]"`. The agent also reported `Ctrl+L` missing; **it exists**,
  citing R8 — I verified and did not pass that on. Three of the four phantom
  bindings are real absences (`Ctrl+X o`, `Ctrl+X ?`, `Ctrl+X 1..9`).
