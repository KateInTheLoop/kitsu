- **Requirement:** none — finishing the production bug fix begun in T0-S18.
  Resolves **F32**.

- **The card tripled in scope before it started, because I surveyed first.** It
  was written as "fix the third `flock` site". Before briefing anyone I ran an
  **exhaustive, untruncated** grep for every `libc::flock` in the workspace —
  the discipline this project already records as a rule, applied *before* being
  wrong rather than after. It found **two more** production sites nobody had
  looked at, because the diagnosis had been scoped to sessions and the previous
  implementer to its own two files.

  Both are quieter than a failed session commit, which is presumably why they
  went unnoticed: `probe_lock` reports a **free** artifact lock as **live**, so
  a reclaimable generation looks in use and is never cleaned up;
  `hold_generation_lock` silently returns "could not acquire", so its caller
  skips work it should have done.

- **The test author nearly proved a site innocent, and caught itself.** Its
  first `probe_lock` regression test **passed**. The reason is subtle:
  `probe_lock` unlocks on success, and `LOCK_UN` releases the **open file
  description** — the very one a forked child inherited. A loop of nothing but
  probes therefore **repairs its own leak** and never observes contention.

  `probe_lock` is only ever wrong about a lock *another* code path leaked. The
  working test uses the production leak source — `hold_generation_lock` taken
  and dropped each attempt, exactly the "run finished, now reclaimable" state a
  sweep inspects — and `continue`s rather than fails if that acquisition itself
  trips, so the two artifact defects stay isolated and fix order does not
  matter.

  **The generalisable form, recorded:** when testing a race in a *reader* of
  shared state, the reader may repair the very condition it is meant to catch.
  Reproducing it needs the real producer of the bad state, not a synthetic
  stand-in. This is the same shape as **F27**, and both times an agent found it
  by noticing its own test passed when it should not have.

- **The structural result matters more than the three fixes.** Verified by my
  own grep after the change: **exactly one `flock(LOCK_EX | LOCK_NB)`
  acquisition remains in the entire production tree**, inside the shared helper.
  Five independent hand-rolled copies of the same wrong inference are now one
  place to be correct — which is what stops a sixth appearing.

- **Review findings and fixes:**
  1. Accepted `pub(crate)` with **no re-export and no move**, on the
     implementer's argument: the three modules are siblings so the path already
     resolves; a crate-root re-export would add a second name for one function
     and hide where it lives; a new module would drag the budget constants and
     the `cfg` block away from the fence callers and their tests. The fully
     qualified call also names the owning module at each site.
  2. Verified rather than accepted: the helper's logic and budget are
     byte-identical (only the signature line changed), no `cfg` moved — the
     `publication.rs` call stays inside `#[cfg(target_os = "linux")]` while the
     helper remains `#[cfg(unix)]` — and `probe_lock` keeps its `LOCK_UN`,
     since only the failure inference was ever wrong.
  3. Each site carries a short comment on why a plain `flock` would be wrong,
     so a reader of `artifacts.rs` or `publication.rs` is not sent to
     `session.rs` to find out.
  4. The one deliberate exception is a test in `tests/cli.rs` that takes the
     lock from the *test* side to simulate a live holder and asserts on the raw
     return. Wrapping it would change what it tests; it stays direct.
