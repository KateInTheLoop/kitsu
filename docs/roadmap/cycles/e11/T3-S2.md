# E11 / T3-S2 — the viewport gets a real config surface, and a config error learns to be helpful without leaking

- **UTC start/end:** 2026-10-14T13:20Z / 2026-10-14T14:43Z
- **Branch/base:** `features/tui_herdr_improvements` / `90570eb`
- **Epic/story/card:** E11 / T3-S2.
- **Requirement:** design **§4.8**, whose risk gate is the unknown-key message.

- **What shipped.** The `[tui]` table with six validated keys (`mode`,
  `alternate_screen`, `prefix`, `title`, `left_arrow_opens_agents`,
  `cell_ring_lines`), the `--tui <classic|inline>` and `--no-alt-screen` flags,
  the **retirement of the `KITSU_TUI` env gate**, and `kitsu doctor` naming a
  bad key. The inline viewport stops being an env-var preview and becomes a
  configurable renderer.

- **Four decisions the test author made from evidence rather than preference:**
  1. **`KITSU_TUI` removed**, because it was read in exactly **one** place and
     keeping it would mean three sources for one setting with no written
     precedence — **F45**'s exact failure shape. The cost is one release-note
     line: a preview adopter falls back to `classic`, which is the safe side.
  2. **Precedence pinned in both directions:** `--tui` beats `[tui] mode` beats
     the `classic` default, with no fourth source; `--no-alt-screen` is a
     one-way force to `never` and its absence forces nothing.
  3. **Defaults from design §4.8**, with `mode = classic` mandated — nothing may
     make inline the default until a human completes Q1's live terminal matrix.
  4. **`cell_ring_lines` bounded `1..=1_000_000`, with `0` an error** rather
     than meaning "disabled", because overloading zero makes "no scrollback"
     indistinguishable from a typo. If a disabled ring is ever wanted it should
     be a mode, not a magic value.

  **It also corrected my brief.** I wrote that a *non-boolean*
  `alternate_screen` should be rejected; the design specifies the tri-state
  `auto|always|never` in **four** places, so a **boolean** is the error. It
  followed the design and flagged the mismatch. Third time this epic a delegate
  has corrected me with evidence.

  **`fullscreen` is rejected until T5**, with the test marked for deliberate
  change then. A value that parses and silently behaves as `inline` is exactly
  the quiet coercion this card's risk gate exists to prevent.

- **The sharpest part of the card was a security constraint nobody had written
  down.** `Config::load` suppresses error detail unless the message starts with
  `unknown field`, replacing it with "(source excerpt withheld to avoid echoing
  credentials)" — deliberate, because **a config file holds gateway tokens and a
  parser error can quote the offending value**.

  The tests required a bad `[tui]` value to **name its key**, which meant
  widening that suppression — and widening it naively leaks: serde's
  `invalid type: string "sk-…", expected a boolean` contains the secret.

  The implementation's answer is `.map_err(|_| …)`, which **drops** serde's
  error rather than wrapping it, so the value never propagates at all; each
  field's `deserialize_with` substitutes a message the codebase owns, carrying
  only the key name and the permitted set. The allow-list then admits exactly
  two classes: serde's `unknown field` (names only) and the local
  `TUI_VALUE_ERROR` prefix. **Serde's `unknown variant` was deliberately left
  suppressed**, because it echoes the word the user typed.

- **Review: I asked for the remaining trade to be closed rather than accepted.**
  The implementer reported, honestly, that leaving `unknown variant` suppressed
  cost the UX of the **most likely typo in the table** — `mode = "inlien"`
  reached `doctor` as "source excerpt withheld" plus a line number, strictly
  less help than a `title` typo got. It offered to allow-list the message.

  **I refused the allow-list and asked for its own pattern to be applied twice
  more**, so `mode` and `alternate_screen` produce a key-naming message listing
  permitted values without interpolating the input. That needed no allow-list
  change and made all six keys fail identically. I authorised the three test
  expectations this required.

  **Verified by me, both properties at once:**
  ```
  [tui] mode = "inlien"          → invalid value for `[tui]` key `mode`: expected one of `classic`, `inline`
  [tui] mode = "sk-SECRETTOKEN"  → invalid value for `[tui]` key `mode`: expected one of `classic`, `inline`
                                   (occurrences of the token in the output: 0)
  ```
  The identical message for both inputs is the point: maximum help with zero
  disclosure, rather than a trade between them.

  **One asymmetry made deliberate rather than accidental:** `--tui` *does* echo
  a bad value, which is right — a shell argument is not a config file and the
  user just typed it — and it is now a stated decision.

- **Dead code retired properly.** Removing the env gate made
  `tui_bridge::mode_from_value` dead, and the test author left both it and its
  passing test in place because it was forbidden to modify tests. **I authorised
  deleting them together**: removing a test for deleted code is not weakening an
  assertion, while keeping a green test for dead code is worse and an
  `allow(dead_code)` would be a lie about why it is there. Its fail-closed
  semantics were also *wrong* for this card — a value the user typed on purpose
  must be a loud error, not a silent fallback to classic.

  The four keys no surface consumes yet are **really read** at the install site
  rather than marked `allow(dead_code)`, so none is silently unreachable until
  T3-S6/T4/T5 arrive.
