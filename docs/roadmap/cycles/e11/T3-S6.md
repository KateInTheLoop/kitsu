# E11 / T3-S6 — the bounded cell ring, and a requirement that overpromised

- **UTC start/end:** 2026-10-14T16:45Z / 2026-10-14T21:25Z
- **Branch/base:** `features/tui_herdr_improvements` / `bbf7570`
- **Epic/story/card:** E11 / T3-S6.
- **Requirement:** **N4**, which this card **amends**. Records **F52**.

- **What shipped.** `kitsu-tui/src/cells.rs`: a bounded, fd-tagged cell ring
  that evicts oldest-first at a configured limit, storing the surface's bytes
  verbatim and deriving the stripped form on demand. It consumes the
  `[tui] cell_ring_lines` key T3-S2 added, which until now was validated but
  unused.

- **Three design decisions, each settled with evidence rather than preference.**
  1. **It lives in `kitsu-tui`, not `kitsu-render`.** The renderer crate
     depends on neither sibling, so it cannot reach the viewport crate — and the
     ring's readers (the transcript overlay, the `[` dump) are TUI concerns.
     Putting it in `kitsu-render` would place an overlay-only structure in the
     crate whose entire job is the classic byte contract. **Fifth consecutive
     card where the plan's stated file was under-specified or wrong**; the
     pattern is now reliable enough to check first.
  2. **Ownership is an opt-in field on the backend, not a process global.**
     `InlineSurface::with_cell_ring` beside `new`; a surface built the ordinary
     way has no ring and reports `None`. The consequence is the good part:
     `ClassicSurface` **cannot name `CellRing` at all**, so "classic pays
     nothing for this" is a **compile-time property** rather than a runtime
     guard or a reviewer's promise.
  3. **A stored line is styled bytes verbatim, stripped on demand.**
     `transcript_line`'s documented contract is already "final bytes, styling
     included, written verbatim"; the overlay repaints these rows, so storing
     stripped text would silently decolour it; and because the ring is the
     **only** copy, styling can be stripped later but never reconstructed. The
     `--plain` tier's structural-marker substitution is deliberately **not**
     applied — that is an output transform, not a storage one.

- **The locking choice is better than the obvious one.** The ring sits behind the
  backend's existing mutex and is pushed **after** the bytes are written and
  flushed, inside the critical section already open for that write. The obvious
  alternative — a separate mutex taken after the write guard drops — would keep
  the ring out of the byte path but would let two threads land their pushes in
  the **opposite order from their bytes**. Since the ring is the sole record, and
  one test asserts interleaved order, sharing the lock makes "retained order ==
  written order" **structural**. The added work is one deque push, one
  allocation and at most one pop: no I/O, no syscall, no call back into user
  code, and the flush still happens first so write latency is unchanged.

- **N4 overpromised, and was amended rather than patched (F52).** It reads
  "**Memory** MUST be bounded by a configurable cell ring (default 10 000
  **lines**)" — two different claims. The ring caps lines; memory is lines ×
  line length, and nothing bounds the second factor. The implementer confirmed
  it plainly: a single 50 MB unbroken line is retained whole, so ten thousand of
  them is unbounded.

  **I did not add a clamp**, because it is not free: the ring is the sole source
  for the overlay and the `[` dump, so truncating a line destroys content
  nothing else retains. That is a product trade — a hard ceiling bought with
  silent loss of the widest lines, which are often the ones worth reading — and
  it deserves a decision, not a patch slipped into an unrelated card. N4 now
  says the bound is in lines, says a pathological line still costs what it
  costs, and names the clamp as a deliberate trade.

  The implementer's two cautions for that future card are recorded in **F52**,
  and the second is the sharp one: **the assertion worth writing is "a clamped
  line is marked", not `len() <= cap`** — a length test passes for an
  implementation that lies about what it kept.

- **The ring is deliberately NOT fed in production.** Nothing reads it until
  **R6**'s transcript overlay, a T5 story, so feeding it would spend up to ten
  thousand styled lines of memory for no benefit. Last card wired the status row
  precisely *because* it had a user-visible payoff; this one has none yet, and an
  honest marker beats premature wiring. The implementer also noted something
  scrupulous: both marked items are `pub` in a library crate, so the lint would
  **not** have fired on them anyway — the markers are documentation, not lint
  silencing, and nothing was wired to quiet a warning.

- **Small implementation care worth recording:** eviction happens **before**
  the append, so the retained count never exceeds the bound even momentarily,
  and the loop is a `while` rather than an `if` so a ring somehow over its
  bound converges instead of staying over.
