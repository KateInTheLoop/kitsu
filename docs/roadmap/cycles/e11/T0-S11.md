# E11 / T0-S11 — the viewport follows a resize, and steps aside when it cannot

- **UTC start/end:** 2026-10-14T02:40Z / 2026-10-14T03:29Z
- **Branch/base:** `features/tui_herdr_improvements` / `4a3840c`
- **Epic/story/card:** E11 / T0-S11
- **Requirement:** R2. Resolves the **resize half of F16**; raises **F24** and
  **F25**.

- **What shipped.** Resizing the terminal re-pins the viewport: the row follows
  the new bottom, the transcript scrolls in the full new height, and the draft
  survives. `DECSTBM` margins are absolute row numbers, so a resized window
  invalidates them and the region has to be **re-set** rather than patched.

- **The decision this card had to make.** A resize can cross F19's minimum
  height in either direction and nobody had decided what should happen. Taken
  here: **below the bound the viewport releases entirely** — region reset, rows
  cleared, nothing pinned — and re-installs when there is room again. A pinned
  row that cannot be drawn correctly is worse than no pinned row, and the
  alternative, keeping a region whose margins no longer fit the screen, is
  precisely the corruption F19 exists to prevent. A test pins the tall → short →
  short → tall round trip, including that the second short resize emits nothing
  and the re-install emits no spurious teardown.

- **One pair, not four branches.** A resize turns out to be the suspend/resume
  pair at new dimensions, minus the paint — the test author established this and
  the pinned bytes say so. Because `hide` is inert without a latched geometry
  and `show` is inert below the bound, all four plan arms fall out of a single
  hide-then-show. It emits **no paint**: a resize happens mid-read, so the row's
  content is the live draft, and painting the status would show a frame of the
  wrong thing before the reader redraws.

  The decision itself is a pure function, `plan_resize`, pinned by a property
  test over `rows 0..=40 × viewport_rows 0..=8` asserting a plan pins a
  geometry **iff** `show` would emit one — so the plan and F19's bound cannot
  drift apart, which is the failure mode a hand-written table would invite.

- **The finding that matters most, and it is untestable here (F24).** The test
  author identified that this feature's delivery mechanism is a `SIGWINCH`
  interrupting the reader's blocking `read` as `EINTR` — and that
  `libc::signal` on Linux/glibc implies **`SA_RESTART`**, which restarts the
  read instead. With that flag the handler still sets the flag and the loop
  **never wakes to check it**, so the viewport silently never resizes while
  every unit test passes, because a test raises the signal from the same thread
  and never blocks in `read`.

  So the correct installation is load-bearing and unverifiable in-repo. Verified
  by reading rather than by report: `sigaction` with `sa_flags = 0`, zero
  `libc::signal` calls anywhere on this path, a handler whose entire body is
  one atomic store, and a boxed comment **at the assignment itself** stating the
  symptom — so a later "simplification" reads as a regression rather than
  tidying. It is now the second item on the terminal matrix needing a human,
  after Q1, and the matrix row names the symptom: *the row only moves after you
  press a key*.

- **Review findings and fixes:** none against the agent's work. Two judgement
  calls accepted on their reasoning: `Cell` rather than an atomic for the
  stored dimensions, since the guard is never shared across threads and
  `resize` takes `&self` only because callers hold it by reference; and an
  `installed()` accessor that **derives** the pinned geometry from the stored
  dimensions and the bound rather than keeping a second flag that could
  contradict `show`. The implementer also hit and fixed a clippy lint on the
  handler cast rather than silencing it.
