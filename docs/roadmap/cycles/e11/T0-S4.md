# E11 / T0-S4 — the inline viewport, the first card that draws

- **UTC start/end:** 2026-10-13T21:37Z / 2026-10-13T22:24Z
- **Branch/base:** `features/tui_herdr_improvements` / `e40aab2`
- **Epic/story/card:** E11 / T0-S4, one card.
- **Requirement:** R3 and N6. The shape is Codex's: a small pinned region at
  the bottom holds the composer and status while finished transcript lines flow
  upward into the terminal's own scrollback, so native search and selection
  keep working — which is the reason this design was chosen over an
  alternate-screen renderer in the first place.

- **Two corrections to my own specification, both caught before they cost a
  cycle, and both by reading or running rather than reasoning:**

  1. **The planned acceptance test was impossible.** The plan required the
     emulator's scrollback to hold every transcript line. I checked
     `vt100 0.15.2`'s source **before briefing anyone** and found
     `Grid::scroll_up` pushes to scrollback only when
     `!scroll_region_active()`, which is false whenever a region is set — and
     the viewport sets one. So region-scrolled rows are **discarded**, and an
     agent given that acceptance would have spent a whole cycle chasing a test
     that cannot pass. Recorded as **F13**; the plan's acceptance is corrected.

     This is not a harness quirk. It is design question **Q1** surfacing early:
     whether region-scrolled lines reach native scrollback is
     terminal-dependent, and vt100 faithfully models a terminal where they do
     not. So the screen half is verified in process, the scrollback half is
     pinned **negatively** — a test asserts the emulator drops those rows, with
     a no-region control case proving the region is the cause — and whether a
     *real* terminal keeps them is strictly T0-S6's live matrix. The
     `insert_history` fallback stays unbuilt until that matrix reports, because
     building both mechanisms before measuring which is needed is speculative.

  2. **My byte contract would have staircased on every real terminal.** I
     specified `transcript_line` as `text + "\n"`. But `TuiRuntime::enter`
     enables raw mode, which clears `ONLCR`, so a bare line feed moves down
     without returning to column zero. The test author found it by running the
     emulator, compensated inside its helper, and **said plainly that the test
     therefore no longer proved the contract sufficient** — which is what made
     the defect visible rather than latent. Corrected to `text + "\r\n"`, the
     compensation removed, and the author regressed its own stub to a bare line
     feed to confirm three tests now go red. Recorded as **F14** with the
     principle that recurs: **each backend supplies its own line ending.**
     `ClassicSurface` is right to emit a bare feed because cooked mode's
     `ONLCR` adds the return; `write_block` guarantees nothing, because the
     block owns its bytes, and a test pins that asymmetry on purpose.

- **Evidence and expected failure:** 10 tests written first;
  `error[E0432]: unresolved import super::InlineSurface`. The author verified
  all 22 (12 existing plus 10) against a throwaway stub and reverted it.

- **In scope:** `InlineSurface` with injectable per-descriptor sinks, `show`,
  `hide`, `paint`, and the two `Surface` methods.
- **Out of scope, each recorded rather than inherited:** resize (**F16**), row
  truncation (**F16**), the live-row conflict (**F15**), and the
  `insert_history` fallback (**F13**).

- **Decisions worth recording:**
  - The viewport's control bytes go to **stderr**, which the test author chose
    and I agree with: the live row is painted there, and `kitsu chat > file`
    must not receive escape sequences in the file.
  - `paint` before `show` is a **no-op**. The bottom row is an `Option`, and
    guessing one would emit absolute cursor positions that scribble over live
    transcript rows. Doing nothing is the only unspecified-case behaviour that
    cannot corrupt the screen.
  - `write_block` runs the block against a local buffer with **no lock held**,
    then takes the mutex to write. A block may re-enter the surface — the
    trait's own docs warn of it — and holding a non-reentrant mutex across that
    call would self-deadlock. Verified by reading the code.
  - The mutex ignores poisoning, so a panic mid-write cannot strand the
    terminal in a pinned region.

- **Tests added or changed:** 10 added, none changed. The sharpest is the
  emulator test: after `show`, forty alternating lines across both descriptors,
  then a three-row paint, it asserts the bottom three rows are exactly the
  painted rows, that the newest line survives in the region and the oldest is
  gone, and that the viewport was never overwritten. The author also pinned
  that the region's last row is blank, explaining why (the final line's own
  feed scrolls once more) so the next reader does not read it as a bug.
