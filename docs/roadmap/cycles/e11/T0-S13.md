# E11 / T0-S13 — rows are fitted to the terminal before they are drawn

- **UTC start/end:** 2026-10-14T03:48Z / 2026-10-14T04:30Z
- **Branch/base:** `features/tui_herdr_improvements` / `3d087c8`
- **Epic/story/card:** E11 / T0-S13. First of three, in a **forced** order —
  see the note in `findings.md`.
- **Requirement:** R2. **Closes F16 entirely**; records **F27**.

- **Why this had to come first.** `paint` wrote each row with no width limit,
  and its own comment admitted it. With a single pinned row an over-long row
  merely wraps untidily; with the several rows the composer and palette need,
  **it wraps into and overwrites the row below**. Building a multi-row composer
  on an unbounded `paint` would have meant debugging corruption that has
  nothing to do with the composer.

- **What shipped.** `kitsu_render::fit_row_to_width(row, cols)`, escape-aware
  and sitting beside the width primitives it reuses, plus `paint` taking
  `cols` and applying it per row. Six numbered rules in application order, the
  ordering itself pinned by a test:
  **byte-identity first** (a fitting row returns byte-identical, with no
  allocation path reachable); escapes cost zero columns; visible columns use the
  existing `char_display_width`; a wide character is never split and the
  leftover column stays unpadded; exactly one reset, only when **both**
  truncated **and** carrying SGR; zero columns yields nothing unless the row was
  already zero-width.

- **Byte-identity was the property to protect, and it is first by construction.**
  Every existing `paint` test asserts exact bytes and the project's output-tier
  discipline rests on byte-comparability, so a fitter that rewrote short rows
  would have broken both quietly. Two of the twelve tests are pure regression
  nets for it and pass against the stub — correctly, since they pin what must
  *not* change.

- **A decision the test author escalated rather than guessed.** It left open
  which escapes count as "styling" for the reset rule, noting that both
  "any escape" and "SGR specifically" passed its tests. Decided **SGR
  specifically**: the reset exists to stop colour and attributes bleeding, and
  only SGR leaves such state behind, so a reset after a cursor move or an OSC
  sequence would be bytes emitted for no reason into a stream other tests
  assert exactly. The reasoning is in a comment ending "do not simplify this to
  any-escape".

- **F27, and it is the most reusable thing here.** The obvious test for this
  defect is **vacuous**: paint a two-row viewport with a long first row and
  assert the second is intact, and it passes *even unfitted*, because the second
  row's own clear erases the smear before writing. The author found this while
  trying to write the card's own test and built two shapes that do observe it —
  a **partial repaint** (what a keystroke actually does, leaving the row below
  unrepaired) and an **overflow on the last row** (nothing below it to repair
  anything, so it wraps off the bottom and scrolls the screen). The general
  lesson is recorded: a repaint-based renderer repairs its own damage on the
  next full pass, so a green full-repaint test is weak evidence.

- **Review findings and fixes:**
  1. The implementer reported **two failing tests as wrong expectations rather
     than editing them**, which is the correct move — and since "the test is
     wrong" is the convenient conclusion, I verified both independently rather
     than accepting them. Both held up.
     - The styled case expected seven columns of text at `cols = 8`; the fit
       correctly fills all eight, and the sibling render test pins exactly that
       full-fill behaviour. The literal had dropped a trailing space.
     - The last-row case asserted the transcript at screen index 0.
  2. **My own investigation went further than the implementer's on the second
     one.** It proposed index 1, attributing the shift to the 15-character
     fixture autowrapping in a 12-column terminal. True, but not the whole
     cause: the cursor is parked on the region's **last** row, so writing any
     line there scrolls the region once by itself — the assertion was wrong
     *independent of the width*. I shortened the fixture so it cannot wrap,
     which isolates the viewport's effect from the fixture's, and confirmed the
     line lands at index **2**. I also rewrote the assertion message, which
     claimed "the transcript did not scroll" — false, since one scroll is
     expected and is the transcript's own newline. It now states what it proves:
     no *further* scroll, and that a last row wrapping off the bottom would
     shift it one row higher.
