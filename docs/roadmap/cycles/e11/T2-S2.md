- **A scope correction I owed.** The plan's T2-S1 row scoped the task-local
  **and** routing `Permissions::resolve`, with a three-case y/a/n test for the
  fs gate. The shipped T2-S1 (`c4bd57b`) delivered only the seam and
  deliberately left the `sender` off `Registry`, because defining it needs the
  request and answer types. So S1 was marked done while half its row was not.
  This card closes that, and does **both** gates together: they are symmetric,
  they share the channel, and B2 specifies both. Nothing regressed in between —
  verified that no production code sets a `Registry` route.

- **The shape, chosen by the test author with reasons I accepted.** One
  `PromptRequest { agent_id, payload, reply }` with
  `PromptRequestPayload::{Path, Command}`, a single `Decision` answer
  vocabulary, and a `oneshot` reply on the request. One type rather than two
  because the registry receiver, the `Blocked { request }` phase, T2-S4's
  `answer(id, Decision)` and T2-S6's timeline entry all need **one** thing to
  hold and **one** match to render; the payload enum keeps the asymmetric
  question while the envelope stays shared. The `oneshot` makes "dropped
  receiver ⇒ `Interrupt`" automatic, so cancellation and B3's timeout need no
  extra signalling path, and it cannot be answered twice. An unbounded channel
  so a permission gate can never fail closed because of backpressure —
  backpressure belongs to the registry's record limits. And the `kitsu` crate
  is still never named: the agent stays a bare `u64`, as in T2-S1.

- **The security property, and why it is now hard to break.** B2 requires that
  `always` apply through **the existing** grant code, adding no escalation
  path. Two things make that real rather than asserted:

  1. **The tests pin post-state, not implementation.** A test cannot see which
     function ran, so after `allow always` they require a sibling path to pass
     a **plain foreground** `check_read` with no further request, and a
     **foreground** `execute_command` of the same invocation to succeed with no
     new request. A background-only grant table would pass a naive
     "was it allowed?" check and **fail** these.
  2. **The implementation produces no second code path at all.** The routed arm
     only converts the parked answer into the same `Decision` the prompter
     would have returned, then falls into the **pre-existing** decision match.
     So `AllowAlways` reaches the original `insert_minimal_root` /
     `insert_grant` arms, and a denial is formatted by the very same
     `format!`. Verified by reading: one deny formatter per gate, and
     `permissions.rs:1665` builds its message with the action interpolated —
     which is why a literal grep for it returns nothing and I had to look
     properly rather than trust a zero.

  The consequence is that byte-identical denial is guaranteed **by
  construction**, not maintained by a test. There is no second message to keep
  in sync.

- **The deny tests do not hardcode a message.** They run the foreground path
  with a denying prompter, capture whatever error it produces, and require the
  routed path to match byte-for-byte. If the foreground wording ever changes,
  the routed path is held to the new wording automatically.
