## 🔴 Critical / Correctness Bugs

### 1. `enforce_context_budget` is fundamentally broken — it never elides anything (`orchestrator.rs`)

```rust
let is_protected = messages[i].role == Role::System
    || Some(i) == last_user_idx
    || messages[i].role != Role::Tool;   // ← BUG
if messages[i].role == Role::Tool && !is_protected {
```

The third clause `messages[i].role != Role::Tool` makes *every non-Tool message protected*, which is fine — but then `is_protected` is `true` for any non-Tool message, and `false` only for Tool messages. So the guard becomes:

- For a Tool message: `is_protected = (System? false) || (last_user? false) || (Tool != Tool → false)` = **`false`**
- The condition `role == Tool && !is_protected` = `true && true` = elides. OK so far...

But the real problem: **the intent of the third clause is unclear and wrong**. A Tool message is *never* `last_user_idx` (different role) and never `System`, so `is_protected` for a Tool message is always `false`, and the `!= Role::Tool` clause is pure dead logic that *only* matters for non-Tool messages — which you already gate out with `role == Role::Tool`. The whole `is_protected` computation is redundant and confusing.

More importantly, **there is no protection against an unbounded loop of elided-but-still-too-large context**: if all tool messages are already elided and `current > max_bytes` (e.g. a huge system prompt + user message), the `while` exits via `i >= messages.len()` — fine — but you've done O(n) work re-scanning. Acceptable, but the logic should be:

```rust
fn enforce_context_budget(messages: &mut [ChatMessage], max_bytes: usize) {
    let mut current: usize = messages.iter().map(|m| m.byte_size()).sum();
    if current <= max_bytes {
        return;
    }
    let last_user_idx = messages.iter().rposition(|m| m.role == Role::User);

    for i in 0..messages.len() {
        if current <= max_bytes {
            break;
        }
        if messages[i].role != Role::Tool || Some(i) == last_user_idx {
            continue;
        }
        let elided = ChatMessage::tool(
            messages[i].tool_call_id.clone().unwrap_or_default(),
            "[older tool output elided]",
        );
        let new = elided.byte_size();
        let old = messages[i].byte_size();
        current = current - old + new;
        messages[i] = elided;
    }
}
```

Also: re-eliding an already-elided message (e.g. when called every round) wastes a tiny bit but is harmless since the string is identical. Consider skipping messages whose content already equals the sentinel.

### 2. `byte_size()` undercounts and can't enforce a real budget (`types.rs`)

`byte_size` sums only `content` + ids + tool-call field lengths. The **actual wire payload** includes JSON structure, role strings, repeated keys, and — critically — the *system prompt and full message envelope*. The budget is described as "context byte budget" but measures something far smaller than what's actually sent. For an MVP this is "approximate" as documented, but be aware the 128 KiB budget will let through substantially more than 128 KiB on the wire. Document the discrepancy or add a fixed per-message overhead constant.

### 3. `FinishReason::Length` returns silently as success (`orchestrator.rs`)

```rust
FinishReason::Stop | FinishReason::Length => return Ok(assistant_text),
```

A `Length` finish means the model was **truncated mid-output**. Returning it indistinguishably from `Stop` means the user gets a silently cut-off answer with no signal. At minimum append a marker (as you do for max-rounds), or surface it. This is a correctness/UX bug.

## 🟠 Error Handling (project forbids unwrap/expect/panic)

### 4. `unwrap_or_default()` on response bodies is fine, but check these (`openai_compat.rs`)

```rust
let body = response.text().await.unwrap_or_default();
```

`unwrap_or_default()` is *not* `unwrap()` — it's safe. ✅ No panic. Good.

### 5. `1 << (attempt - 1)` can overflow / the backoff math is wrong (`openai_compat.rs`)

```rust
let backoff = Duration::from_millis(200 * (1 << (attempt - 1)).min(8));
```

Precedence bug: `.min(8)` binds to `(1 << (attempt - 1))`, **not** to `200 * ...`. So this caps the *shift result* at 8, giving max `200 * 8 = 1600ms`. That's probably the intent — but it's accidental and fragile. More importantly, with a large `retries` config, `1 << (attempt - 1)` can shift past 31 and **panic in debug / overflow in release**. Since `attempt` is bounded by `self.retries` (config-controlled, `u32`), a misconfigured `retries: 64` will panic. Clamp the shift:

```rust
let shift = (attempt - 1).min(3);
let backoff = Duration::from_millis(200 * (1u64 << shift));
```

This is a **panic path** reachable via config — violates the no-panic rule.

### 6. Timeout-retry loop ignores backoff and can spin (`openai_compat.rs`)

```rust
Err(e) => {
    if e.is_timeout() && attempt < self.retries {
        attempt += 1;
        continue;   // ← no sleep, immediate retry
    }
```

Timeout retries have no backoff (unlike 429/503). Minor, but inconsistent. Add a sleep here too.

### 7. `main.rs` uses `tracing_subscriber` but it's not in `kitsu-core`/etc — verify `anyhow` is actually used

`crates/kitsu/Cargo.toml` lists `anyhow` and `chrono` but `main.rs`/`config.rs` don't appear to use either (`CliError` is hand-rolled, no `anyhow`; chrono only in providers). Dead dependencies — remove them to reduce surface. Minor.

## 🟡 Security (tokens must never leak)

### 8. `set_sensitive(true)` is good, but `StaticAuth.token` and `EnvBearerAuth` leak via `Debug` (`auth.rs`)

Neither `StaticAuth` nor `EnvBearerAuth` derives `Debug` (good — they can't be accidentally logged via `{:?}`). But **`AuthConfig` derives `Debug`** (`config.rs`) and contains `token: Option<String>`:

```rust
#[derive(Debug, Clone, Deserialize)]
pub struct AuthConfig {
    ...
    pub token: Option<String>,
}
```

And `Gateway` derives `Debug`, and `Config` derives `Debug`. If anyone ever does `tracing::debug!(?config)` or `eprintln!("{config:?}")`, **the static token leaks to logs**. This directly violates "auth tokens must never leak/log." Fix: implement `Debug` manually for `AuthConfig` redacting `token`, or wrap it in a `Redacted<String>` newtype:

```rust
impl std::fmt::Debug for AuthConfig {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        f.debug_struct("AuthConfig")
            .field("method", &self.method)
            .field("token", &self.token.as_ref().map(|_| "<redacted>"))
            // ...
            .finish()
    }
}
```

### 9. `ProviderError::Http { body }` may echo back sensitive data (`error.rs` / `openai_compat.rs`)

The comment claims "never contains the (sensitive) token," but the *error body from the gateway* is fully captured and printed to stderr via `eprintln!("{e}")` in `main.rs`. Gateways sometimes echo request headers or auth context in error bodies. Low risk, but consider truncating the body and noting it's untrusted. Not blocking.

## 🟢 API / Async Design

### 10. `chat_stream` doesn't actually stream — it buffers the whole body (`openai_compat.rs`)

```rust
let text = response.text().await.map_err(map_send_error)?;
let deltas = if req.stream { parse_sse(&text) } else { ... };
let s = stream::iter(deltas.into_iter().map(Ok));
```

The function returns a `ChatStream` (`BoxStream`) but **fully buffers the response** before yielding any delta. So `--stream` gives no incremental output to the user despite `print_fragment` being called per-fragment — all fragments arrive at once after the whole response lands. This defeats the entire streaming UX. The doc comment ("real gateways stream it") acknowledges this is a stopgap. For an MVP it's a known limitation, but it should be flagged loudly: **streaming is currently fake**. The real fix is to consume `response.bytes_stream()` and parse SSE incrementally.

### 11. `refresh_hint()` calls `self.auth.header()` a second time (`openai_compat.rs`)

On a 401, you call `header()` again purely to extract the hint:

```rust
fn refresh_hint(&self) -> Option<String> {
    match self.auth.header() {
        Err(AuthError::Missing { hint, .. }) => hint,
        _ => None,
    }
}
```

This re-reads the env var and **re-allocates the token**. Functionally fine, but consider having the `AuthProvider` trait expose `refresh_hint()` directly rather than reconstructing the header to fish out the hint. Minor design smell.

### 12. `tool_descriptors` always returns `None` — tools are dead in the loop (`orchestrator.rs`)

```rust
fn tool_descriptors(_tools: &Registry) -> Option<Vec<ToolDescriptor>> {
    None
}
```

The orchestrator runs tools returned by the model, but **never advertises any tools**, so a compliant model will never request them. The whole tool-calling path is currently unreachable in practice. This is documented as future work, but the `Registry` should carry descriptors (it only holds `HandlerFn`). The loop and registry are out of sync — `Registry` needs a `descriptors()` method before tools can work end-to-end.

## 🔵 Simplifications / Minor

- **`orchestrator.rs`**: The `match finish { Stop | Length => ..., ToolCalls => ... }` arms when `tool_calls.is_empty()` all return `Ok(assistant_text)` — collapse to a single `return Ok(...)` (after adding the `Length` marker from issue #3).
- **`auth.rs`**: `EnvBearerAuth` and `StaticAuth` share identical header-building logic. Extract a free function `build_header(header: &str, scheme: &str, token: &str, env_for_err: &str)`.
